# React の画面の実装に共通する条件

この条件は、実行の担当が develop-react-frontend で、業務の資料と backend の契約から画面と操作を書いた repository（以下、コード）を判定するためのもので、どのお題にも当てる。ケースに固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しいコードの中身は書かない。担当が書いたコードが一つも無いときは、コードを読む条件はすべて FAIL とする。

重み3は利用者の原則の芯（画面は業務を決めない、外から来た値を丸めない、業務の言葉、差し替えは外部と時計と採番だけ、公開するのは使うものだけ、コメントは自分の責務だけ、書く前に書かずに済む道を探す）、重み2は画面の骨組み、重み1は細部である。

### screen-does-not-decide

重み: 3

PASS：画面は、backend が返した一覧を返った順のまま描き、並べ替え、絞り込み、集計を足していない。操作を拒む理由を画面で作らず、backend が返した業務の拒否の文言を言い換えずに見せている。資料に無い表示や操作を足していない。

FAIL：画面で並べ替え、絞り込み、集計をしている。または、拒む理由を画面で判定しているか、backend の文言を言い換えている。または、資料に無い表示か操作がある。

### no-rounding-outside-values

重み: 3

PASS：backend の応答と URL のような外から来た値を、入口で一度 schema に通し、契約に合わない値（知らない種類、形の違う識別子）を既定の表示や「未指定」へ丸めずに throw するか誤りとして見せている。有限の値は union の型にし、`never` まで網羅した分岐で知らない値を throw している。

FAIL：契約に合わない値を既定の表示へ丸めている。または、有限の値を string のまま持つか、網羅しない分岐で知らない値を通している。

### result-kinds-by-screen-action

重み: 2

PASS：操作の結果は、画面のすることが変わる単位の判別できる union（成功、業務の拒否、利用上限のように）で、画面は種類を網羅して描き分ける。業務の拒否では文言を見せ、成功の後は一覧の持ち主に読み直させ、画面の側で一覧を推測で書き換えていない。

FAIL：結果を bool や例外だけで表している。または、成功の後に画面の側で一覧を書き換えている。または、種類の描き分けに漏れがある。

### form-and-leaf

重み: 2

PASS：form で表せる操作は `<form action>` と submit の button で書き、結果を `useActionState` で受けている。click handler と `useTransition` で独自の送信の仕組みを作っていない。状態を持つ部品を操作の要る最小の部品に留め、結果から表示への写しのような JSX に依らない判断を純粋な関数に切り出している。

FAIL：独自の送信の仕組みを作っている。または、純粋な関数に切り出せる判断が部品の中に埋まっている。

### naming-business-language

重み: 3

PASS：部品、hook、関数、型の名前は、業務の資料の語（英名があればその英名）から付けられている。データや処理の形から付けた名前（`Data`、`Info`、`Manager`、`Item`、`handleXxx` だけで業務の意味を持たない名前の類）が、業務の概念を表す名前として使われていない。

FAIL：業務の概念を表す型か部品か関数に、形や処理から付けた名前がある。

### test-doubles-only-external

重み: 3

PASS：テストで差し替えているのは、制御できない外部（backend の HTTP を MSW で）だけで、自分の部品、hook、関数、backend を呼ぶ自分の関数を `vi.mock` や偽物で差し替えていない。テストは role、accessible name、表示された文のような利用者が観測できるもので確かめている。テストのためだけに実装へ公開の口や分岐を足していない。

FAIL：自分のモジュールを `vi.mock` か偽物で差し替えている。または、実装の内部の状態や class 名で確かめている。または、テストのためだけの口が実装にある。

### tests-at-smallest-layer

重み: 2

PASS：純粋な関数は単体のテストで分岐を確かめ、表示の部品はその部品の状態ごとに確かめ、同じ観点を複数の層で重ねていない。業務の境界値を画面のテストで網羅していない。

FAIL：純粋な関数の分岐を部品のテストだけで確かめている。または、同じ観点を複数の層で重ねている。

### public-only-used

重み: 3

PASS：export は、ほかのモジュールかテストが業務の振る舞いを確かめるために使うものだけである。どこからも使われない export と、テストで内部を見るためだけの export が無い。

FAIL：どこからも使われない export か、テストで内部を見るためだけの export がある。

### comments-own-responsibility

重み: 3

PASS：コメントは、その部品や関数自身の意味と責務（業務上の意味、シグネチャから読めない契約）だけを書いている。使う側の都合（「〜が呼ぶ」「〜が差し替える」）、担わないものを誰が担うか、存在の理由を実装の事情に帰する断り書き（「資料に無い」「実装の都合」）が無い。外部の API の振る舞いのように、その関数の分岐を読むのに要る事実を書くことは、断り書きに当たらない。

FAIL：上のどれかに当たるコメントが一つでもある。

### lazy-reuse-before-writing

重み: 3

PASS：作業の前から repository にあったもので済む責務（backend を呼ぶ関数、識別子の schema、認証のトークンの扱い）を探して使っている。使われない引数、呼ばれない分岐、将来のための枠や TODO、理由の言えない抽象を書いていない。

FAIL：作業の前からあった同じ責務のものを自分で書き直している。または、将来のための足場か理由の無い抽象がある。
