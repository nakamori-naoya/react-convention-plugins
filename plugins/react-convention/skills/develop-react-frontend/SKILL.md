# develop-react-frontend

React 19 の画面の表示と利用者の操作を、一つずつ、テストと実装の一続きで仕上げる。実行基盤（TanStack Start、React Router、Server Components を使わない SPA など）が違っても判断は同じである。API の書き方は、対象 repository が使う版の公式の資料で確かめる。

## 画面は業務の資料を写し、業務を決めない

フロントエンドは、業務の資料から見せるものと操作を受け取る。ユーザージャーニーの場面が画面と遷移になり、URL はその場面を指す。何をどの順で見せるかは、業務知識のクエリとクエリデータモデルが決める。画面は読み取りの結果をその順のまま描き、並べ替え、絞り込み、集計を足さない。足すと、同じ読み取りの規則が backend と画面の二か所に分かれ、backend のテストで守った順が画面で崩れる。

利用者の操作とそれを拒む理由は、業務知識のコマンドが決める。画面は拒む理由を作らず、backend が返した業務の拒否の文言をそのまま見せる。その文言は、backend が業務知識の拒む理由の語で持っているので、画面で言い換えると同じ理由に語が二つできる。部品、hook、型の名前は、development-convention の write-readable-code に従って業務の言葉で付ける。

資料に無い表示や操作が要ると分かったら、画面で補わずに止まり、資料への提案として返す。

## 秘密はServerの内側に閉じ、Serverの入口は外から叩かれるものとして書く

ブラウザへ渡すのは、表示に要る直列化できる値（DTO、ID、有限の状態）と Server Function の参照だけにする。session の token、秘密、backend と通信する client、生成されたメッセージの class はブラウザへ出さない。ブラウザに届いた値は表示のための写しで、次の操作を許す証拠にはならない。

Server Function は、画面の button から呼ぶ関数に見えても、外から直接叩ける入口である。Server Components を使わない構成では、ブラウザが呼ぶ HTTP の入口が同じ立場にある。だから入口の内側で入力を検証し、session から主体を得て backend へ渡し、主体が無ければその場で login の画面へ移す。route guard は利用者を案内するためのもので、守りの根拠にしない。

その主体に操作を許すか（認可）は、業務を実行する backend が一か所で決め、Server Function で重ねて判定しない。二か所で判定すると、いずれ食い違うからである。Server Function が backend を介さずに保存先へ触るなら、それが backend なので、層の判断は development-convention の apply-layer-convention に従う。入口ごとの認証、利用上限、偽装要求（CSRF）への対策を宣言するのは development-convention の protect-entry-points で、実装はその宣言を実行基盤が用意する仕組みで満たす。

## 読み取りの持ち主は一つにし、更新の後はその持ち主に読み直させる

初期表示の読み取りは route が持つ。Server Components が使えるなら、route の loader が GET の Server Function を呼び、Server Component で描く。Client の cache に持たせるのは、読み取りの入力がブラウザにしか無いか、表示中に取り直し続けることが要求のときだけで、そのときは初期表示から Client が持つ。Server が初期表示を描き Client の cache が続きを持つ分け方をすると、同じ事実を二つの cache が持ち、どちらが正しいかが描画の順で変わる。

状態を変える操作は POST の Server Function に置き、GET では状態を変えない。GET は先読みや再試行で何度も呼ばれうるからである。操作が成功したら読み取りの持ち主に読み直させ（route の再検証など）、画面の側で結果を推測して書き換えない。書き換えると、クエリデータモデルが決めた見せ方を画面で作り直すことになる。

一つの画面にある独立した読み取りは、意味のある区画（Section）に分けて並行に始め、待機（Suspense）と失敗（Error Boundary）の境界を区画ごとに置く。一つの区画の失敗で、画面の全体を止めない。

## 外から来た値は入口で一度だけ検証し、丸めない

URL の parameter、form の値、backend の応答、browser storage の値は、入った入口で一つの schema に通す。値が無いときの既定値が仕様で決まっていれば、それを使う。値があるのに型や範囲が合わなければ、既定値や「未指定」へ丸めない。URL なら誤った指定であることを見せ、form ならその入力に結び付けた誤りを返し、backend の応答なら想定外の失敗として throw する。丸めると、壊れた入力が正しい操作に化け、原因が誰にも見えなくなる。router が値を先に数値などへ解釈することがあるので、schema は router が渡す形を受けてから検証する。

業務の概念は string や number のまま持たず、有限の値は union の型にする。未知の値は、`never` まで網羅した switch で throw する。

URL に置くのは、再読込、共有、戻る操作で再現すべき状態（検索語、絞り込み、一覧の続き）だけである。browser storage は、URL、Server の読み取り、局所の state のどれでも表せない値（未送信の下書き、利用者が選んだ表示の設定）にだけ使い、秘密と認可の根拠は置かない。

## 操作の結果は、画面のすることが変わる単位の有限の型にする

Server Function は、成功と予測できる失敗を判別できる union（`{ kind: "borrowed" }`、`{ kind: "rejected", message }` のような形）で返し、画面は種類を網羅して描き分ける。種類の分け目は、画面のすることが変わるかである。業務の拒否なら文言を見せて入力を残し、競合なら読み直しを促し、利用上限なら時間を置いてもらう。backend の拒む理由を一つずつ種類にはしない。未認証と未登録は、種類として画面へ返さず、入口で遷移させる。

送った後に応答が途切れた（接続の断、期限切れ）なら、それは失敗ではなく、結果が分からない状態である。反映されているかもしれないので、同じ操作を促さず、読み取りの持ち主に読み直させて今の状態を見せる。壊れた応答と未知の種類は、成功や既定の表示へ丸めずに throw し、Error Boundary に受けさせる。

form で表せる操作は、`<form action>` と submit の button で書き、結果を `useActionState` で受ける。click handler と `useTransition` で独自の送信の仕組みを作らない。利用者の操作なしに POST すること自体が要求のとき（外部の認証から戻った直後の登録など）だけ、Effect から一度だけ呼んでよい。

## 描画は純粋に保ち、Clientは最小の葉にする

Client にするのは、利用者の event、ブラウザの API、state、送信中の表示が要る最小の葉だけである。Client の部品を子に持つことは、親を Client にする理由にならない。部品は、表示だけを担うもの（有限の状態、DTO、callback を props で受ける）と、Server Function、router、認証の SDK とつなぐものに分ける。JSX に依らない判断（結果から表示の状態への写し、backend の応答から結果の種類への写し、操作の組み立て）は、純粋な関数に切り出す。この分け方が、そのままテストの分担になる。

導出できる値は state に置かず、描画中に計算する。Effect は外部システムとの同期だけに使う。React Compiler を使うなら、`memo`、`useMemo`、`useCallback` を予防で足さず、Compiler の診断を黙らせない。

## テストは、失敗を再現できる最小の層に一度だけ書く

差し替えてよい境界と、最小の層に置く原則は、testing-strategy の design-test-strategy の test-strategy-judgment.md が持つ。差し替えてよいのは制御できない外部、時計、採番だけなので、自分の部品、hook、Server Function、router、自分の backend は差し替えない。外部の HTTP を差し替えるときは、MSW のように要求と応答の形で差し替える仕組みを使う。

React ではこれを次のように当てる。純粋な関数は、単体テストで全分岐を確かめる。表示だけを担う部品は、有限の状態ごとの story とその browser test で、見た目、一つの操作、accessibility を確かめる。props だけで状態を作れるので、何も差し替えずに済む。Server Function、router、backend をつなぐ配線は、production build に実際の認証と backend をつないだ E2E で確かめ、業務の境界値はそこで網羅しない。つなぐ部品を Server Function や router の偽物で包んだ部品のテストは書かない。偽物が本物とずれても緑のままだからである。どの経路を E2E に残すかは testing-strategy の design-e2e-test-scenarios が決め、E2E のテストはそのシナリオの ID を名前に持つ。

テストは、利用者が観測できるもの（role、accessible name、表示された文、外へ渡した callback の引数）で確かめる。テストのために実装を曲げないことは、write-readable-code に従う。

## 進め方と止まるとき

対象 repository の AGENTS.md、package.json、設定から、実行基盤、認証の SDK、React Compiler の採否、テストの道具、完了判定の command を読む。依頼の場面に当たる業務の資料を読み、任意の `references` は最初に読む。画面や操作ごとに、受け取る資料、読み取りの持ち主、Client にする葉、入口で検証する値、結果の種類を決める。純粋な関数と表示の部品はテストを先に書いて失敗を確かめてから実装し、完了判定の command を実行する。認証か操作の経路を変えたなら、E2E も実行する。

この skill はコードを変えるので、欠けた情報が実装を変えるときは推測で埋めずに止まり、分からない点と提案を返す。見せるものとその順、拒む理由、場面の遷移が資料から決まらないとき、外から来る値の許される範囲が決まっていないとき、自分のコードを差し替えなければテストを書けない構造のときがこれに当たる。部品の分け方や名前の揺れでは止まらず、最も筋の良い形を採って報告に書く。

変更したファイル、画面と操作ごとに決めたこと、テストを置いた層、完了判定の結果、止まった点と提案を報告する。

## 判断例（図書館の貸出）

「借りている本」の画面は、ユーザージャーニーの場面の一つである。route の loader が GET の Server Function を呼び、Server Component がクエリデータモデルの順（返却期限の早い順）のまま、資料番号と返却期限と延滞かどうかを描く。「借りる」の button だけが Client の葉で、form から POST の Server Function を呼ぶ。Server Function は session の利用者として backend へ借りる要求を送り、延滞で拒まれたら backend の文言をそのまま `rejected` で返す。応答が途切れたら結果が分からない状態として読み直し、成功したら route を再検証する。本を借りる画面の URL の資料番号が形に合わなければ、丸めずに誤った指定であることを見せる。結果から表示の状態への写しは単体テストで、一覧の表示の状態は story で確かめ、ログインして本を借り「借りている本」に現れるまでの一本だけを E2E に残す。
