# develop-react-frontend

React 19 の画面の表示と利用者の操作を、一つずつ、テストと実装の一続きで仕上げる。最初に、表示する業務結果と読み取りの持ち主、操作の入口と結果の種類、入力・応答の契約違反をどこで表すかを決める。ここが分かれれば、通信断で結果が分からない場合と、受け取った値が契約に違反した場合を混ぜずに済む。実行基盤（TanStack Start、React Router、Server Components を使わない SPA など）が違っても判断は同じである。API の書き方は、対象 repository が使う版の公式の資料で確かめる。

## 画面は業務の資料を写し、業務を決めない

フロントエンドは、業務の資料から見せるものと操作を受け取る。ユーザージャーニーの場面が画面と遷移になり、URL はその場面を指す。何をどの順で見せるかは、業務知識のクエリとクエリデータモデルが決める。画面は読み取りの結果をその順のまま描き、並べ替え、絞り込み、集計を足さない。足すと、同じ読み取りの規則が backend と画面の二か所に分かれ、backend のテストで守った順が画面で崩れる。

利用者の操作とそれを拒む理由は、業務知識のコマンドが決める。画面は拒む理由を作らず、backend が返した業務の拒否の文言をそのまま見せる。その文言は、backend が業務知識の拒む理由の語で持っているので、画面で言い換えると同じ理由に語が二つできる。部品、hook、型の名前は、development-convention の write-readable-code に従って業務の言葉で付ける。

資料に無い表示や操作が要ると分かったら、画面で補わずに止まり、資料への提案として返す。

## 秘密と認可はブラウザの表示から切り離す

Server がある構成では、ブラウザへ渡すのは表示に要る直列化できる値と Server Function の参照だけにする。session の token、秘密、backend と通信する client は Server に閉じる。SPA がブラウザから backend を呼ぶ構成では、公開してよい認証情報だけをブラウザの認証基盤から得る。いずれもブラウザに届いた表示値や操作の可否は、次の操作を許す証拠にはならない。

Server Function は、画面の button から呼ぶ関数に見えても、外から直接叩ける入口である。SPA では、ブラウザが呼ぶ backend の HTTP の入口が同じ立場にある。だからその入口で入力と主体を検証し、主体が無ければ認証の経路へ移す。route guard は利用者を案内するためのもので、守りの根拠にしない。

その主体に操作を許すか（認可）は、業務を実行する backend が一か所で決め、画面や Server Function で重ねて判定しない。二か所で判定すると、いずれ食い違うからである。Server Function が backend を介さずに保存先へ触るなら、それが backend なので、層の判断は development-convention の apply-layer-convention に従う。入口ごとの認証、利用上限、偽装要求（CSRF）への対策を宣言するのは development-convention の protect-entry-points で、実装はその宣言を実行基盤が用意する仕組みで満たす。

## 読み取りの持ち主は一つにし、更新の後はその持ち主に読み直させる

初期表示の読み取りは、実行基盤が提供する画面の読み取り境界に置く。Server Components を使える構成なら Server で描き、SPA なら Client の読み取り状態が初期表示から再読込まで持つ。表示中に取り直し続ける必要がある場合も、同じ持ち主に一貫して任せる。Server が初期表示を描き Client の cache が続きを持つ分け方をすると、同じ事実を二つの cache が持ち、どちらが正しいかが描画の順で変わる。

状態を変える操作は、Server Function がある構成では POST に、SPA では backend の更新用入口に置き、GET では状態を変えない。GET は先読みや再試行で何度も呼ばれうるからである。操作が成功したら読み取りの持ち主に読み直させ（route の再検証など）、画面の側で結果を推測して書き換えない。書き換えると、クエリデータモデルが決めた見せ方を画面で作り直すことになる。即時の反映が要求されるときは、確定前の表示と読み取り結果を区別し、失敗時に戻せる形で扱う。

一つの画面にある独立した読み取りは、意味のある区画に分けて並行に始める。待機と失敗の境界は、その区画だけで復旧できる単位に置く。一つの区画の失敗で、無関係な区画まで止めない。

## 外から来た値は入口で一度だけ検証し、丸めない

URL の parameter、form の値、backend の応答、browser storage の値は、入った入口で一つの schema に通す。値が無いときの既定値が仕様で決まっていれば、それを使う。値があるのに型や範囲が合わなければ、既定値や「未指定」へ丸めない。URL なら誤った指定であることを見せ、form ならその入力に結び付けた誤りを返し、backend の応答なら想定外の失敗として throw する。丸めると、壊れた入力が正しい操作に化け、原因が誰にも見えなくなる。router が値を先に数値などへ解釈することがあるので、schema は router が渡す形を受けてから検証する。

業務の概念は string や number のまま持たず、有限の値は union の型にする。未知の値は、`never` まで網羅した switch で throw する。

URL に置くのは、再読込、共有、戻る操作で再現すべき状態（検索語、絞り込み、一覧の続き）だけである。browser storage は、URL、Server の読み取り、局所の state のどれでも表せない値（未送信の下書き、利用者が選んだ表示の設定）にだけ使い、秘密と認可の根拠は置かない。

## 操作の結果は、画面のすることが変わる単位の有限の型にする

操作の結果は、成功と予測できる失敗を判別できる union で受け、画面は種類を網羅して描き分ける。種類の分け目は、画面のすることが変わるかである。業務の拒否なら文言を見せて入力を残し、競合なら読み直しを促し、利用上限なら時間を置いてもらう。backend の拒む理由を一つずつ種類にはしない。未認証など、画面を離れるべき結果は認証の入口で遷移させる。

送った後に応答が途切れた（接続の断、期限切れ）なら、それは失敗ではなく、結果が分からない状態である。反映されているかもしれないので、同じ操作を促さず、読み取りの持ち主に読み直させて今の状態を見せる。壊れた応答と未知の種類は、成功や既定の表示へ丸めずに throw し、Error Boundary に受けさせる。

form で表せる操作は、`<form action>` と submit の button で書き、結果を `useActionState` で受ける。業務の拒否後に入力を残すなら、action が返った後に非制御の入力が reset されることを踏まえて設計する。form では表せない非同期の操作は event から始め、必要な間だけ `useTransition` で進行状態を扱う。同じ操作の重複送信を防ぎ、結果は操作した場所で読めるようにする。利用者の操作なしに更新すること自体が要求のときだけ、Effect から呼んでよい。その場合も Effect の再実行で操作が重複しないことを、入口の契約で確かめる。

## 描画は純粋に保ち、Clientは最小の葉にする

Server Components を使う構成では、Client にするのは、利用者の event、ブラウザの API、state、送信中の表示が要る最小の葉だけである。その葉は実行基盤が要求する Client 境界を明示し、Hook を使う部品が Server 側に組み込まれていないか build の生成物でも確かめる。Client の部品を子に持つことは、親を Client にする理由にならない。SPA でも部品は、表示だけを担うもの（有限の状態、DTO、callback を props で受ける）と、通信、router、認証の SDK とつなぐものに分ける。JSX に依らない判断は、純粋な関数に切り出す。この分け方が、そのままテストの分担になる。

配置も変更理由に合わせる。route は URL と読み取り・描画の接続、Server Function は外から呼べる入口、Server 専用の処理は秘密と backend との通信、機能の部品は表示・操作・純粋な判断をそれぞれ持つ。同じ機能のコードとテストは近くに置く。実行基盤が違えばディレクトリ名を合わせる必要はないが、入口と Server 専用処理を画面の部品に混ぜると、秘密や入力検証の境界を追えなくなる。

導出できる値は state に置かず、描画中に計算する。Effect は外部システムとの同期だけに使う。React Compiler を使うなら、`memo`、`useMemo`、`useCallback` を予防で足さず、Compiler の診断を黙らせない。

## テストは、失敗を再現できる最小の層に一度だけ書く

差し替えてよい境界と、最小の層に置く原則は、testing-strategy の design-test-strategy が持つ。自分の部品、hook、Server Function、router は差し替えない。backend が別の配備単位なら、その HTTP 境界を差し替えてよい。

React ではこれを次のように当てる。純粋な関数は、単体テストで意味のある分岐を確かめる。表示だけを担う部品は、対象 repository が持つ component test または story の browser test で、表示、操作、accessibility を確かめる。props だけで状態を作れるので、通信を差し替えずに済む。SPA で backend が別の配備単位なら HTTP の境界を差し替え、実際の画面操作から要求と表示を確かめられる。Server Function や router を介す配線は、production build に実際の認証と backend をつないだ E2E で確かめ、業務の境界値はそこで網羅しない。自分の入口を偽物で包んだテストが通っても、実際の配線は確かめられない。どの経路を E2E に残すかは testing-strategy の design-e2e-test-scenarios が決める。

テストは、利用者が観測できるもの（role、accessible name、表示された文、外へ渡した callback の引数）で確かめる。テストのために実装を曲げないことは、write-readable-code に従う。

## 進め方と止まるとき

対象 repository の AGENTS.md、package.json、設定から、実行基盤、認証、テストの道具、完了判定の command を読む。依頼の場面に当たる業務の資料を読み、必要な `references` を読む。画面や操作ごとに、受け取る資料、読み取りの持ち主、入口で検証する値、結果の種類を決める。失敗を観測できるテストを先に書いてから実装し、完了判定の command を実行する。認証か操作の経路を変えたなら、E2E も実行する。最後に業務の場面から表示・操作・失敗時の結果の抜けを探し、追加した部品と状態から資料へ戻って、今は要らないものを外す。整えた後は完了判定を通す。

この skill はコードを変えるので、欠けた情報が実装を変えるときは推測で埋めずに止まり、分からない点と提案を返す。見せるものとその順、拒む理由、場面の遷移が資料から決まらないとき、外から来る値の許される範囲が決まっていないとき、自分のコードを差し替えなければテストを書けない構造のときがこれに当たる。部品の分け方や名前の揺れでは止まらず、最も筋の良い形を採って報告に書く。

変更したファイル、画面と操作ごとに決めたこと、テストを置いた層、完了判定の結果、止まった点と提案を報告する。
