# test-react-ui

読み終えたagentは、Reactの画面、Server Function、部品の振る舞いを、それを最も安く確かめられる一つの層へ割り当て、その層の形でテストを書ける。

## 本質

この規約の大半は、次の三つから導かれる。

一つの振る舞いは、それを確かめられる最も安い一つの層で確かめる。この原則と、固定の時間ではなく観測できる条件を期限付きで待つという原則は、repositoryのテスト戦略（`testing-strategy` package の `design-test-strategy`）が持つ。このskillは、Reactのテストでの形だけを持つ。

自分のコードは実物を使う。差し替えてよいのは、テストの環境に無いものと、外部との通信やSDKの呼び出しのように制御できない境界だけである。自分のコードを差し替えたテストは、差し替えた分だけ本物を確かめていない。

テストは利用者が観測できるもの（role、accessible name、表示された状態、外へ渡したcallback）で確かめ、実装の内部（propsの呼び出し順、内部のstate）に依らない。

## 入力

対象repositoryの絶対pathと、テストを書く・直す対象（部品、画面、Server Function、変更差分）を受け取る。任意の `references` は追加で従う資料の絶対path配列で、最初に読む。repositoryが使うテストの道具（単体テスト、storyとbrowser test、E2Eの道具）、外部通信の差し替えの道具、完了判定のcommandは、対象repositoryのAGENTS.md、package.json、設定fileから読む。repositoryにテスト戦略の資料があれば、それも読む。

## 判断基準

### どの層で確かめるか

JSXやDOMに依らず、同じ入力から同じ結果を返す判断（状態遷移、値の変換、URLのschema）は、単体テストで全分岐を確かめる。表示だけを担う部品の有限の状態、見た目の違い、一つの操作、accessibilityは、その部品のstoryとbrowser testで確かめる。Server Functionと、Serverでreadを持つ部品の、認可、成功、予測できる失敗、遷移先は、Serverの境界を直接呼ぶテストで確かめる。Actionを持つClient部品の、送信中の表示、結果の反映、失敗からの回復は、部品のテストで確かめる。実際の認証、redirect、backend、データベースをまたぐ主要な経路だけを、E2Eで確かめる。どの経路をE2Eへ残すかは、repositoryのテスト戦略の決定に従う。詳しくは [層の割り当て](references/layer-assignment.md) に従う。

### 同じことを二つの層で確かめていないか

重複を下の層へ寄せる原則はテスト戦略に従う。Reactでの形は、storyとbrowser testで確かめた表示や操作を単体テストで繰り返さないこと、Serverの境界で確かめた認可の分岐をClient部品のmockで複製しないことである。

### 何を差し替えてよいか

自分のコード（部品、hook、Server Function、Providerのmodule）は差し替えない。差し替えてよいのは三つだけである。テストの環境に無いmodule（挙動を足さない空の置き換え）。実行時に外部と通信するかSDKを呼ぶ境界（ブラウザに無いAPIを含む）。時刻の源。外部との通信は、HTTPの契約を経由して差し替える道具（MSWなど）を優先する。呼び出しを観測するだけの関数（`vi.fn` など）は、外部の境界へ渡すcallbackだけに使う。手で書く偽物は、本物の型と、成功、失敗、空の値を表す契約のfixtureとして一か所に置く。詳しくは [差し替えと待機](references/doubles-and-waiting.md) に従う。

### 何で確かめるか

roleとaccessible nameで要素を探し、利用者に見える表示の状態と、外へ渡したcallbackの引数で確かめる。外部の境界への呼び出しの回数だけを合格の条件にしない。storyの操作のテストも、利用者が観測できることだけを確かめる。

### どう待つか

待機の原則はテスト戦略に従う。Reactのテストでは、`findBy...` や、条件を渡した `waitFor` のような待機付きの問い合わせで、表示が現れる、buttonが押せる、状態が変わるまでを待つ。固定のsleepが要るように見えたら、テストの側で隠さず報告する。

## 手順

1. **道具と規約を読む。** `references` と、対象repositoryのAGENTS.md、package.json、テストの設定、テスト戦略の資料を読む。
2. **振る舞いを列挙して層へ割り当てる。** 対象の振る舞いを、判断、表示の状態、Serverの境界の分岐、Actionの状態、主要な経路に分け、それぞれを一つの層へ割り当てる。既存のテストと重なるものは、どちらに残すかを決める。
3. **テストを書く。** 割り当てた層の形で書く。自分のコードは実物を使い、外部の境界だけを差し替える。
4. **検証する。** 対象repositoryの完了判定のcommandを実行する。storyや表示だけの部品を変えたなら、browser testも実行する。

## 停止条件

このskillはコードを変えるので、分からない点に出会ったら推測で埋めずに止まり、何が分からないかと提案を返す。止まるのは、確かめるべき振る舞い（期待する表示、失敗の種類、認可の規則）が資料からもコードからも決まらないとき、repositoryのテストの道具や完了判定が読み取れないとき、自分のコードを差し替えなければ書けない構造になっているとき（その場合は、差し替えずに書ける形への変更を提案する）、完了判定のcommandが失敗して直せないときである。

## 出力

書いた・直したテストのfile、振る舞いごとに割り当てた層と理由、差し替えた外部の境界、消した重複、実行した完了判定の結果、止まった点と提案を報告する。
